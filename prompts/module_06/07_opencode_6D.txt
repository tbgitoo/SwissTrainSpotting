Task:
Implement **Phase 6D only** of Module 6 — Testing & Validation for OCR.

Goal:
Add the smallest useful set of tests that validates the OCR module behavior in a credible, maintainable way, without redesigning the OCR feature or broadening the repository unnecessarily.

Required scope:
1. Add JVM unit tests for `OcrTextNormalizer`
2. Add instrumentation tests for OCR UI behavior in `ImageClassificationActivity`, using a stub/fake OCR analyzer rather than depending on real ML Kit runtime behavior
3. Validate the key Module 6 behaviors:
   - empty OCR stays hidden
   - non-empty OCR is shown
   - OCR does not overwrite classification result text
   - OCR failure or empty result does not crash the app
   - OCR integration remains auxiliary and non-blocking in behavior

Do NOT implement:
- new OCR production features
- new layout redesign
- analyzer refactors beyond tiny testability seams if absolutely necessary
- ML Kit runtime integration tests against the real recognizer
- broad refactoring of `ImageClassificationActivity`
- changes to ONNX inference logic
- changes to routing logic
- Phase 6A/6B/6C redesign
- new activities, fragments, ViewModels, Compose, or Kotlin

Testing strategy constraints:
- Prefer deterministic tests over ambitious or flaky tests
- Use a stub/fake `OcrAnalyzer` for instrumentation tests
- Do not rely on network, cloud, or Play Services runtime state
- Do not attempt OCR accuracy benchmarking
- Do not create a large custom test framework
- Keep names explicit and review-friendly

Required unit test coverage for `OcrTextNormalizer`:
- blank input -> empty
- whitespace-only input -> empty
- leading/trailing whitespace trimmed
- repeated internal whitespace collapsed
- multi-line input normalized according to the current implementation rule
- already clean input preserved
- null handling tested explicitly if the implementation exposes it

Required instrumentation/UI test coverage:
1. empty OCR result keeps OCR section hidden
2. non-empty OCR result shows OCR section and displays OCR text
3. OCR text appears only in the OCR section, not inside the classification result TextView
4. OCR failure-equivalent path (empty/null or fake failure behavior) does not break the activity
5. if feasible without broad refactoring: delayed OCR result does not prevent classification text from appearing
