## Specific planning requirements

### 1. Module definition
The plan must define clearly what Module 5 does and does not do.

It should cover:
- consuming the preprocessed float tensor from Module 3
- loading an ONNX model from Android app assets/resources
- creating and managing an ONNX Runtime session
- running inference
- parsing model output
- returning a minimal result object or equivalent result seam suitable for UI use

It must explicitly exclude:
- training
- ONNX export
- OCR
- image acquisition / EXIF
- backend
- complex persistence
- unrelated UI redesign

---

### 2. Two-phase sequencing
The plan must make the 5A / 5B sequencing operational, not just narrative.

It must explain:
- why a known-good reference model is used first
- what exact risks this isolates
- what should be considered “done” for 5A
- what changes in 5B and what must remain stable

This is important:
5A should validate the Android inference path independently from project-model uncertainty.

---

### 3. ONNX Runtime / Android integration seam
The plan must define a plausible Android/Java seam for inference integration.

It should consider and decide things like:
- where the ONNX Runtime session should live
- whether there should be a small dedicated wrapper/helper class
- how model loading from resources should happen
- how `float[]` from Module 3 becomes ONNX input
- how result parsing returns something usable by the UI

The seam should stay simple and repo-appropriate.
Do not invent architecture layers unless clearly justified.

---

### 4. Packed-vs-planar correctness
The plan must explicitly address:
- Module 3 output is planar NCHW float data
- ONNX input shape/layout expectations must match this
- common mistakes the implementation must avoid:
  - HWC/NHWC confusion
  - interleaved RGB assumptions
  - wrong tensor shape
  - wrong input name
  - wrong cardinality
  - output interpretation drift

This should appear in the plan’s pitfalls / guardrails / testing sections.

---

### 5. Serious testing strategy
This is critical.

The plan must include a serious Android-side testing strategy up to integration level.

It should cover at least:

#### Unit / narrow tests where possible
Examples:
- model session creation path
- basic contract checks around input tensor length / expected shape
- label loading sanity
- predictable output parsing behavior where testing can be isolated

#### Instrumented Android tests
Examples:
- load reference model from real Android resources
- run inference on synthetic or controlled input tensors
- run preprocessing + inference on real Android test image asset

#### Integration tests
The plan should explicitly include at least one realistic integration path using:

- `app/src/androidTest/assets/metro_flon.png`

This image should be used for an Android-side integration test such as:
- decode asset to `Bitmap`
- preprocess using Module 3
- run Module 5 inference
- assert no exception
- assert output shape / result structure / top-k parsing sanity
- optionally assert deterministic repeatability of top prediction if appropriate for the reference model

The plan must be careful not to claim semantic correctness for Swiss train classes when using the reference model.
The integration test should be framed as inference-path validation, not final domain validation.

### 6. Testing philosophy
The plan should make clear that Module 5 can fail in ways that are:

The plan should not be casual about testing.
