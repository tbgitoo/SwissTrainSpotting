## Goal
Evolve the current Module 5A implementation so that the app can load a **model family via explicit configuration/profile**, instead of assuming one fixed generic model asset layout.

For this task, support at least:
- the existing generic MobileNetV2/ImageNet family
- one exported specialized family such as `hymenoptera`

This phase is about **configuration-based model-family loading**, not multi-model runtime coexistence.

---

## What Phase 5B must achieve

Phase 5B must make it possible to load a model family through configuration, where a family includes:

- ONNX model file
- labels file
- metadata file (when present)

The app must no longer assume that all models use:
- the same asset filenames
- the same label format
- the same metadata assumptions

## Required implementation direction

### 1. Introduce model profile/config concept
Add the smallest clean mechanism needed to represent a model family.

A profile must be able to describe, at minimum:
- profile id
- model asset path
- labels asset path
- whether labels are plain text or JSON artifact family
- metadata asset path if present
- input/output node names or whether these come from metadata

This can be done with:
- a small config class
- or equivalent minimal structure

Do not overengineer this into a framework.

### 2. Support generic and specialized families
Support at least these two cases:

#### Generic Phase 5A family
- `mobilenetv2.onnx`
- `imagenet_classes.txt`
- no required metadata JSON
- existing constants remain acceptable here

#### Specialized exported family
Example:
- `hymenoptera.onnx`
- `hymenoptera_labels.json`
- `hymenoptera_model_metadata.json`

For specialized families, metadata must drive:
- model file
- labels file
- node names
- class count

### 3. Label loading must handle both formats
Extend or adapt label loading so that:
- plain text labels still work for ImageNet-style model
- JSON exported labels work for `*_labels.json` artifact family

Do not duplicate unrelated logic.
Keep the implementation minimal and local.

### 4. Metadata-aware loading
For exported families, parse metadata and use it to configure model loading.

At minimum use:
- `model_file`
- `labels_file`
- `input_name`
- `output_name`
- `num_classes`

Do not ignore metadata and re-hardcode the same values elsewhere.

### 5. One active model profile at a time
This phase still uses one active classifier/session at runtime.

Do not implement multiple active sessions yet.
Do not preload both generic and specialized models in this task.
