# Module 2 — Image Acquisition & Permissions Implementation Plan

**Status:** Planning  
**Depends on:** Module 1 (two-activity UI shell)  
**Reference:** `../plans/01_architecture.md`, `AGENTS.md`  
**Target:** Java + XML, `minSdk 24`, no backend, no persistence

---

## 1. Module purpose

Enable the user to acquire a train/loco photo from either the **system photo picker** or the **device camera**, then **display that image** on `ImageClassificationActivity`.

This module completes the “capture / select → visible image” step in the global pipeline:

```
USER → Capture / Select image → Bitmap → [Module 3+] Preprocessing → ONNX → OCR (optional)
```

**Module 2 deliverable:** a reliably loaded, displayable in-memory `Bitmap` (held on the classification screen for the current session), plus the `Uri` it was decoded from when applicable. The image should appear upright in the UI so later modules receive a bitmap that matches what the user saw.

**Milestone:** user taps **Image** or **Camera** on the home screen, completes picker or capture, and sees their photo in the preview area — without crash, without storage permissions for gallery, and with only the minimal camera permission when capture is used.

## 3. Recommended acquisition strategy

Use the **Activity Result API** (`registerForActivityResult`) already supported via the existing `androidx.activity` dependency. Avoid deprecated `startActivityForResult`.

### 3.1 Gallery — system photo picker (primary path)

**Contract:** `ActivityResultContracts.PickVisualMedia()` with `PickVisualMedia.ImageOnly`.

**Why:** On API 24+ (project `minSdk`), the photo picker grants temporary read access to the chosen item. No storage permission is declared or requested. This matches the global architecture assumption (“System photo picker — no storage permissions required”).

**Flow:**

1. User taps **Image** on `MainActivity`.
2. `MainActivity` starts `ImageClassificationActivity` with an intent extra, e.g. `EXTRA_ACQUISITION_MODE = GALLERY`.
3. `ImageClassificationActivity` immediately launches the photo picker (after `onCreate`, once launchers are registered).
4. On success: receive `Uri` → decode to `Bitmap` → apply EXIF rotation if needed → set on `ImageView`, store in a field `selectedBitmap`.
5. On cancel: show placeholder state and a short message; user can go back and try again.

**Fallback (only if picker unavailable on a test device):** `ActivityResultContracts.GetContent()` with `"image/*"`. Do not add storage permissions for this fallback; if it fails on a specific device, document in testing notes rather than broadening permissions.

### 3.2 Camera — standard capture intent (secondary path)

**Contract:** `ActivityResultContracts.TakePicture()` **or** `StartActivityForResult` wrapping `MediaStore.ACTION_IMAGE_CAPTURE` with `EXTRA_OUTPUT` pointing to a `FileProvider` `Uri`.

**Recommended:** `TakePicture()` takes a destination `Uri` and returns `Boolean` success — simpler than parsing a thumbnail from result data.

**Why not CameraX:** Architecture and project constraints require minimal risk; intent-based capture is one permission, no preview UI to build, and sufficient for spotter use.

**Ephemeral file (strictly necessary):**

- Create a temp JPEG in `getCacheDir()` (e.g. `camera_capture.jpg`), overwritten on each capture.
- Register `FileProvider` in manifest with `cache-path` in `res/xml/file_paths.xml`.
- Pass provider `Uri` to the capture contract.
- After success, decode the same `Uri` to `Bitmap` for display and session hold.

This is **not** persistent user storage; cache may be cleared by the system. No copy to MediaStore.

**Flow:**

1. User taps **Camera** on `MainActivity`.
2. `ImageClassificationActivity` opens with `EXTRA_ACQUISITION_MODE = CAMERA`.
3. Check/request `CAMERA` permission (see §5).
4. Launch capture intent with cache `Uri`.
5. On success: decode → EXIF rotate → display → hold `selectedBitmap`.
6. On cancel/deny: placeholder + message; back navigation still works.

### 3.3 Bitmap vs Uri — what to keep in memory

| Artifact | Role in Module 2 | Role for later modules |
|----------|------------------|------------------------|
| `Uri` | Source reference for decode and config restore | Module 3 can re-decode if needed; camera cache `Uri` remains valid for session |
| `Bitmap selectedBitmap` | Display + handoff | Module 5 reads this field (or a getter) after Module 3 adds preprocessing |

**Do not** pass `Bitmap` through intent extras (size limits, duplication). Pass only the **acquisition mode** extra from `MainActivity`; all loading happens in `ImageClassificationActivity`.

### 3.4 EXIF orientation (minimal, acquisition-only)

Gallery and camera JPEGs often carry EXIF orientation. Without correction, the preview appears sideways and Module 3 would train on misaligned pixels.

**Module 2 responsibility:** after decode, apply a small helper (e.g. read EXIF via `ExifInterface` on the `Uri` stream or file path) and rotate the `Bitmap` once so the `ImageView` shows the upright image. Store the **corrected** bitmap in `selectedBitmap`.

**Not Module 2:** scaling to 224×224 or float normalization — those stay in Module 3.

### 3.5 Optional helper class

Extract decode + EXIF logic into one plain Java class (e.g. `ImageLoader` or `BitmapUtils` under `com.tb.swisstrainspotting.util`) to keep the activity readable. No interfaces, no DI — static methods or a small instance class is enough.

## 4. Activity responsibilities

Keep the **two-activity structure** from Module 1. Do not add a dedicated camera activity or fragment.

### 4.1 MainActivity

| Responsibility | Detail |
|----------------|--------|
| Navigation hub | Unchanged visual role: title + two large buttons |
| Mode selection | **Image** → start `ImageClassificationActivity` with `GALLERY` extra |
| | **Camera** → start `ImageClassificationActivity` with `CAMERA` extra |
| Permissions | **Do not** request `CAMERA` here; defer to classification screen so gallery path never triggers camera permission |
| Acquisition logic | **None** — only passes intent extra |

### 4.2 ImageClassificationActivity

| Responsibility | Detail |
|----------------|--------|
| Read intent extra | Determine gallery vs camera on entry |
| Register result launchers | Photo picker + take picture (+ permission launcher if using `RequestPermission`) |
| Trigger acquisition | After launchers registered, auto-start the appropriate flow once per entry (not on every `onResume` unless retry is explicitly added) |
| Permission gate | Camera path: check `CAMERA`; request if missing; launch capture only when granted |
| Decode & rotate | `Uri` → upright `Bitmap` |
| Display | Set `ImageView` (`ivPlaceholder` or rename to `iv_preview` in layout — cosmetic only) with `scaleType` already set (`centerCrop`) |
| Session state | Field: `Bitmap selectedBitmap`, optional `Uri selectedUri` |
| Cancel / error UX | Placeholder drawable + toast string |
| Back navigation | Existing back button unchanged |
| Config changes | Save `selectedUri` (and mode if mid-permission) in `onSaveInstanceState`; restore and re-decode on recreate **or** retain bitmap if small enough — prefer re-decode from `Uri` to limit memory |
| Future hooks | Placeholder comments or empty methods for “Run classification” (Module 5) — **do not implement** |

## 5. Permissions strategy

### 5.1 Manifest declarations

Add only:

```xml
<uses-permission android:name="android.permission.CAMERA" />
```

Optional but harmless for Play/feature clarity:

```xml
<uses-feature android:name="android.hardware.camera" android:required="false" />
```

**Do not add:** `READ_MEDIA_IMAGES`, `READ_EXTERNAL_STORAGE`, `WRITE_EXTERNAL_STORAGE`, `MANAGE_EXTERNAL_STORAGE`.

### 5.2 Runtime behavior

| Path | Permission |
|------|------------|
| Gallery / photo picker | **None** |
| Camera | **`CAMERA`** — request immediately before launching capture, only on camera path |

Use `ActivityResultContracts.RequestPermission()` for a single-permission request. If denied:

- Show a toast (string resource) explaining camera is required for that button.
- Leave placeholder visible.
- Do **not** loop nagging dialogs; user can press Back and use gallery instead.

### 5.3 FileProvider (not a permission)

Declare `androidx.core.content.FileProvider` in manifest with `android:authorities="${applicationId}.fileprovider"`, `exported="false"`, `grantUriPermissions="true"`. Required so the camera app can write the capture output. Document in code comments that this is cache-only, not user album storage.

## 7. Step-by-step implementation workflow

Work in small, testable commits (user-driven); order minimizes integration risk.

### Step 1 — Constants and manifest foundation

1. Add `AcquisitionMode` enum with `GALLERY` and `CAMERA`.
2. Define intent extra key constant on `ImageClassificationActivity` (public static final String).
3. Add `CAMERA` permission and optional `uses-feature` to manifest.
4. Create `file_paths.xml` and register `FileProvider`.
5. **Verify:** project compiles; no behavior change yet.

### Step 2 — Bitmap loading utility

1. Implement `BitmapLoadUtils.loadOrientedBitmap(Context, Uri)`:
   - Open stream via `ContentResolver`.
   - Decode with `BitmapFactory.decodeStream` (consider `inJustDecodeBounds` then single decode if image is huge — cap max dimension for **display** only, e.g. 2048px, to reduce OOM risk without touching 224×224 model logic).
   - Read EXIF orientation; rotate with `Matrix` if needed.
   - Return null on failure; log tag only (no user-facing hardcoded strings in Java).
2. **Unit-testable logic:** pure rotation mapping from EXIF constants can be package-private for later tests (optional in this module).

### Step 3 — MainActivity intent extras

1. Change `btnImage` listener to pass `AcquisitionMode.GALLERY`.
2. Change `btnCamera` listener to pass `AcquisitionMode.CAMERA`.
3. **Manual test:** both buttons still open classification screen (picker not wired yet).

### Step 4 — Gallery path in ImageClassificationActivity

1. Register `PickVisualMedia` launcher in `onCreate` (before `STARTED` state — register early).
2. Read acquisition mode from intent; if `GALLERY`, launch picker once (`boolean acquisitionStarted` flag).
3. On result `Uri`: call utils → set `ImageView` → store `selectedBitmap` / `selectedUri`.
4. On cancel: toast + keep placeholder drawable.
5. **Milestone test:** gallery-only end-to-end on emulator with sample photos.

### Step 5 — Camera path

1. Register `TakePicture` launcher with cache file `Uri` from `FileProvider.getUriForFile(...)`.
2. Register `RequestPermission` for `CAMERA`.
3. If mode is `CAMERA`: check permission → request or launch capture.
4. On capture success: decode cache `Uri` same as gallery path.
5. **Milestone test:** camera on physical device (emulator camera is optional/limited).

### Step 6 — UX polish and strings

1. Move all user-visible text to `strings.xml`.
2. Fix `ImageView` `contentDescription` to `@string/image_preview_description`.
3. Add short toasts for failure modes (decode failed, permission denied).

### Step 7 — Configuration change handling

1. Save `selectedUri` and `acquisitionMode` in `onSaveInstanceState`.
2. On restore: if `selectedUri != null`, re-decode and display (skip re-launching picker unless user explicitly navigated fresh).
3. Guard `acquisitionStarted` so rotation does not reopen picker mid-flow.
4. **Test:** rotate device after image loaded; image remains visible.

### Step 8 — Handoff preparation (no ML code)

1. Add package-private getter `getSelectedBitmap()` on `ImageClassificationActivity` **or** document that Module 3 will read the field — for clarity, a simple getter is enough.
2. Add a one-line comment where Module 5 will trigger classification — **no button or inference**.

### Step 9 — Compile and smoke test

1. `./gradlew :app:assembleDebug` from `SwissTrainSpottingApp/`.
2. Run full manual checklist (§8).

## 9. Risks / likely mistakes

| Risk | Mitigation |
|------|------------|
| **Launching picker in `onResume`** | Use one-shot flag so picker/camera opens only on first entry, not after permission callback conflated with resume |
| **Registering launchers too late** | Register all `registerForActivityResult` calls in `onCreate` before `STARTED` |
| **Passing Bitmap via Intent** | Pass only mode extra; decode in classification activity |
| **Forgetting FileProvider** | Camera capture fails silently or crashes; verify manifest + `meta-data` authority matches code |
| **FileProvider URI permission** | Use `FLAG_GRANT_WRITE_URI_PERMISSION` on capture intent (TakePicture handles this) |
| **OOM on large images** | Display decode with max-edge cap in utils; full-resolution deferral is Module 3 concern if utils and preprocessor share decode |
| **Mixing gallery permission models** | Do not add storage permissions “just in case” |
| **Hardcoded strings** | Violates AGENTS.md; use `strings.xml` |
| **Implementing classification button early** | Scope creep into Module 5 |
| **CameraX / custom preview** | Over-engineering; stick to intent |
| **Saving to MediaStore** | Introduces persistence and permission scope |
| **EXIF skipped** | Sideways preview; Module 3 model sees wrong orientation — apply minimal fix in Module 2 |
| **contentDescription in English in XML** | Move to `@string/` |
| **Duplicate acquisition on rotation** | Save state + guard flags |
| **minSdk 24 vs Photo Picker** | `PickVisualMedia` backports via Google Play services on many devices; keep `GetContent` as documented fallback without extra permissions |
