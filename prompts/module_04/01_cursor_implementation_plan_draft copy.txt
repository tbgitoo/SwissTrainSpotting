## Critical planning constraints

### 1. Dataset layout must be explicitly specified
The plan must define exactly:
- where training images are stored
- how labels are derived
- how datasets are split or organized

Start from the architecture assumption:
- folder-per-class dataset
- `model/data/raw/<class_name>/*.jpg`

The plan must decide and document whether validation is:
- a separate folder tree (e.g. `train/` and `val/`)
- or a scripted split derived from `raw/`

Be explicit. Do not leave dataset organization implicit.

### 2. Label source of truth must be defined
The plan must state:
- labels come from class folder names
- class ordering must be deterministic
- the same ordering must be serialized into `labels.json`
- this ordering must remain consistent with ONNX output index interpretation on Android

Do not leave label ordering as an accidental property of runtime behavior.

### 3. Python ↔ Android preprocessing contract must remain aligned
The plan must explicitly preserve the existing deployment contract already established in the architecture and Android implementation:

- input size: `224x224`
- RGB
- ImageNet normalization
- NCHW
- float32

Very important:
- the architecture intentionally chose **simplified resize-only preprocessing**
- do **not** silently replace this with the usual PyTorch tutorial defaults like `RandomResizedCrop` or `CenterCrop` unless the plan explicitly discusses and rejects/accepts that change

The plan must state how Python preprocessing during:
- training
- validation
- export verification

will be kept compatible with Android inference.

### 4. MobileNetV2 transfer-learning strategy must be decided explicitly
The plan must choose and justify an initial transfer-learning strategy for the small dataset:
- feature extraction first
- or fine-tuning
- or staged approach (e.g. head-only first, optional unfreeze later)

The plan should stay conservative and reproducible rather than aggressively optimized.

### 5. ONNX export contract must be explicit
The plan must define:
- model input name
- model output name
- expected ONNX input shape
- expected output shape
- export path
- Python-side ONNX verification step

Do not leave input/output naming to accidental defaults.

### 6. Metadata artifacts must be planned, not hand-waved
The plan must define what goes into:
- `labels.json`
- `model_metadata.json`

At minimum, metadata should include enough information to validate:
- class names / order
- input size
- normalization used
- tensor layout
- model type/backbone
- export date/version if useful

The metadata should support later Phase 5B model swap without redesign.

### 7. Testing/validation must be part of the plan
The plan must include validation steps for:
- dataset readability / class discovery
- class index ordering
- training sanity checks
- ONNX export success
- Python-side ONNX inference sanity check
- artifact completeness

Do not stop at “model exports” — define how the export is checked before Android asset swap.

## Important guidance

### Use official patterns where appropriate, but adapt them to this project
The official PyTorch transfer-learning material uses pretrained vision models and folder-based datasets, which is relevant. However, this project has a stricter cross-platform preprocessing contract than a generic tutorial. The plan must therefore adapt official practice to repository reality rather than copying tutorial defaults blindly.

### Keep the plan reproducible
Prefer a plan that:
- is deterministic
- is easy to debug
- isolates uncertainty
- produces artifacts that can be validated independently of Android training assumptions

### Preserve separation of concerns
The plan should support the already validated Android inference environment by producing a model that conforms to the established runtime contract, rather than redesigning the Android side around training-time convenience.
